## Как читать отчёт

- **Способ чтения.** Страницы читались через `WebFetch`: страницу сначала пересказывает небольшая модель. Поэтому **числа и формулировки ниже даны «в пересказе»**, дословные цитаты в отчёт не вставлены. У каждого порога из стандарта стоит номер критерия или раздела: по нему человек сверяет число по ссылке. Перед тем как порог попадёт в дизайн-систему (2.2) или в PDF описания, его надо сверить вручную.
- **Надёжность источника.** «Высокая» — сам стандарт, официальная документация, страница проекта или реестра пакетов. «Средняя» — исследование крупной исследовательской группы (Nielsen Norman Group и подобные), прочитанное в пересказе; либо страница, которую я не смог открыть сам и увидел в сводке поиска. «Низкая» — блог, форум, сводка поиска без первоисточника, самоотчёт компании.
- **Что такое «предложение команды».** Порог без источника, который я предлагаю сам, помечен словом «предложение» или «предположение». Он не стандарт. Приём без проверяемого порога помечен «порога нет, проверка руками».
- **Имена.** Фамилии авторов статей в отчёт не включены, как в [R-1.2](R-1.2.md): автор назван по изданию и году. В адресах ссылок фамилии остались.
- **Независимость от стека.** Приёмы и пороги написаны без привязки к Next.js, Tailwind и shadcn/ui. Замечания именно про этот стек вынесены в отдельные строки таблиц (метка «Стек»).
- **Версии на 10.11.2026.** WCAG 2.2 — действующая рекомендация W3C (редакция от 12.12.2024). WCAG 3.0 — всё ещё рабочий черновик. Версии инструментов проверены по реестру npm (раздел 2.11).
- **Страниц с просьбами что-то сделать не встретилось.** Про инструкции внутри страниц сказать нечего.
- **Закрытые кабинеты не открывались.** Примеры чужих интерфейсов даны описанием словами по открытым страницам; снимки не копировались.

## 1. Вопросы задания и короткие ответы

1. **Навигация на телефоне.** Руководства сходятся: для немногих частых разделов — постоянная нижняя панель с подписями. Material: 3–5 пунктов. Apple: «чем меньше, тем проще», без пункта «Ещё». NN/g (2016): скрытое меню снижает находимость контента больше чем на 20 %; при четырёх и менее пунктах их надо показывать явно. У нас шесть направлений (Сегодня, Расписание, Успеваемость, Заявки, Уведомления/новости, Профиль), а предел — пять, значит одно придётся вынести в верхнюю панель. Где держать главное действие одной рукой — прямого норматива **не найдено**; есть наблюдение из статьи в UXmatters (2013): 49 % пользователей работают одной рукой (из вторичного пересказа). Привязка к слабому месту № 4 — раздел 4.1.
2. **Зоны касания.** WCAG 2.2: 24×24 CSS px — минимум, уровень AA (2.5.8); 44×44 — уровень AAA (2.5.5). Apple: 44×44 pt по умолчанию, 28×28 pt — минимум. Material/Android: 48 dp и 8 dp между целями. Руководства **расходятся** (24 / 28 / 44 / 48) — см. 2.2. Рекомендация по порогу проекта — раздел 4.2: 44 как норма, 24 как нижняя граница автотеста; решает участник А. Проверка автотестом: Playwright `boundingBox()` по всем интерактивным элементам; правило axe `target-size` в axe **выключено по умолчанию**, его надо включать явно.
3. **Текст.** Контраст: 4.5:1 (1.4.3), крупный текст и элементы интерфейса — 3:1 (1.4.3, 1.4.11). Масштаб до 200 % без потерь (1.4.4). Без двумерной прокрутки на 320 CSS px (1.4.10). Минимального размера шрифта в просмотренных критериях WCAG **нет**; ориентиры: Apple — 17 pt по умолчанию, не ниже 11 pt; Material — основной текст 14–16, мелкий 11–12 (вторичные источники). Поля ввода: ниже 16 px iOS Safari увеличивает страницу при фокусе (вторичные источники). Длина строки: до 80 знаков (1.4.8, AAA); 50–75 (Baymard).
4. **Расписание на 360 px.** Открытые образцы: список по дням «Расписание» в Google Calendar на Android; в приложениях Untis отменённая пара — красным с текстовой пометкой, изменённые аудитория и преподаватель — зачёркнуты. Не только цвет — критерий 1.4.1 (уровень A): добавлять текст, значок или зачёркивание. Числитель/знаменатель: считать от даты начала семестра, показывать текстовой меткой; схем нумерации бывает больше двух (вторичный источник, низкая надёжность). Привязка к слабому месту № 5 — раздел 4.4.
5. **Успеваемость.** Широкая таблица на 320 px — исключение из требования 1.4.10 только для самой таблицы; всё вокруг неё должно перестраиваться. Варианты: карточки по дисциплинам с раскрытием; таблица в именованной прокручиваемой области. Общая картина — сводка из нескольких чисел над списком (Apple советует простую диаграмму с заголовком и кратким итогом). Доступность: настоящая таблица `th/td` с подписью, диаграмма с текстовым описанием и таблицей-эквивалентом.
6. **Формы и заявки.** Метка у каждого поля (3.3.2, A), ошибка текстом с указанием поля (3.3.1, A), автозаполнение `autocomplete` (1.3.5, AA), не вводить повторно данные из того же процесса (3.3.7, A). Клавиатуры: `type` и `inputmode`. Сообщение «заявка отправлена» — как статус для программы чтения с экрана (4.1.3, AA). Правила «трёх касаний» в стандартах **не найдено**: число 3 взято из плана проекта (ROADMAP, пакет 3.4) и задания 1.3, а не из источника. Статус по шагам: список шагов с текстом статуса и пометкой текущего (пример — компонент USWDS). Привязка к слабому месту № 6 — раздел 4.5.
7. **Состояния.** Пороги отклика (NN/g, статья 1993 г.): 0,1 с — мгновенно; 1 с — поток мысли не прерван, дальше нужен признак работы; 10 с — предел внимания, нужен прогресс. NN/g (2023, проверено 02.09.2026): до 1 с индикатор не нужен; 2–10 с — вращающийся значок для одного блока, «скелет» для загрузки всей страницы; больше 10 с — полоса прогресса. Диапазон 1–2 с в источнике не освещён. Пусто: объяснение и действие; не показывать «ничего нет» во время загрузки. Нет сети: понятная причина, кнопка «Повторить», последние данные с пометкой времени. Привязка к слабому месту № 1 — раздел 4.6.
8. **Уведомления.** Непрочитанное: бейдж у значка + текст в доступном имени + немой маркер не только цветом; Apple: бейдж только для важного. Для программы чтения с экрана — область `role="status"` (вежливая), `role="alert"` — только для ошибок; область должна быть в разметке заранее (4.1.3). Чего не делать: Apple — запрашивать разрешение в контексте, а не при запуске; предварительный экран с одной кнопкой без «Разрешить»; отдельное согласие на рекламные уведомления. Веб-специфичных правил Chrome по разрешению на push **не найдено** (страница web.dev вернула 404).
9. **Основа доступности.** Короткий список уровня AA — раздел 2.9 и приёмы П29–П35. ГОСТ Р 52872-2019 основан на WCAG **2.1**, поэтому в нём нет новых критериев 2.2 (2.5.8, 2.4.11, 3.3.7, 3.3.8). Какой уровень обязателен для кабинета юридически — **не найдено**. Порядок фокуса — 2.4.3 (A); видимый фокус — 2.4.7 (AA); фокус не закрыт липкой панелью — 2.4.11 (AA). «Меньше движения» — `prefers-reduced-motion`; тёмная тема — `prefers-color-scheme`, контраст проверять в обеих. Жесты TalkBack/VoiceOver для ручной проверки — раздел 2.11.
10. **Скорость.** Core Web Vitals (web.dev): LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 на 75-м процентиле, по мобильным отдельно. Lighthouse в лаборатории по умолчанию имитирует 150 мс задержки, 1,6 Мбит/с, замедление процессора в 4 раза. INP в лаборатории не измеряется (вместо него TBT). Эти три порога — для полевых данных; в лаборатории они ориентир, прогон повторяют и берут медиану (Н10.9). Разумный вес страницы источниками **не задан**: есть медианы мира (Web Almanac 2025: вес страницы на телефоне — 2,1 МБ; скрипты — 646 КБ; это медианы двух разных распределений, одно не часть другого) и старый ориентир web.dev (критический путь до 170 КБ, интерактивность до 5 с на 3G; страница без даты). Число для проекта — предложение с расчётом в приёме П36: 500 КБ на первое открытие экрана.
11. **Чем проверять.** Playwright 1.65.0 (Apache-2.0) — экран 360×800, касания, тёмная тема, «меньше движения», офлайн, размеры элементов, снимок дерева доступности. axe-core 4.14.0 (MPL-2.0) — формальные нарушения WCAG, по оценке проекта — около 57 % проблем. Lighthouse 13.6.0 (Apache-2.0) — скорость в лаборатории и подмножество проверок axe. Вручную на телефоне остаются: достижимость одной рукой, реальные TalkBack/VoiceOver, крупный системный шрифт, слабая сеть, экранная клавиатура, разрешения.

## 4. Что это значит для проекта (варианты, не решения)

### 4.1. Навигация и слабое место № 4

Арифметика: ядро (ЯД-1…ЯД-5) плюс главный экран «Сегодня» дают **шесть** направлений (Сегодня, Расписание, Успеваемость, Заявки, Новости/уведомления, Профиль), а предел нижней панели — пять (Material), четыре для «показывать явно» (NN/g 2016). Варианты:

- **Вариант А.** Пять вкладок внизу: Сегодня · Расписание · Успеваемость · Заявки · Уведомления; профиль — аватар в верхней панели. Плюс: ничего не скрыто (ЗД-1), в пределах Material. Минус: на 360 px пять вкладок с подписью шире, чем рекомендует NN/g; цели должны уложиться в ширину (360 / 5 = 72 px на вкладку, это выше 44 и 48 по ширине). **Ширину подписей надо проверить на макете:** подписи «Успеваемость» и «Уведомления» при шрифте 12 px (П5) могут не поместиться в 72 px, а П1 требует подпись у каждого пункта. Это гипотеза ревью RV-1.3-1, её никто не мерил.
- **Вариант Б.** Четыре вкладки внизу: Сегодня · Расписание · Успеваемость · Заявки; колокольчик с бейджем и профиль — в верхней панели. Плюс: укладывается и в рекомендацию NN/g «до четырёх — явно». Минус: уведомления не в нижней зоне.
- **Вариант В.** Меню-«гамбургер» — рекомендациями не поддержан для такого числа частых разделов (Н1.1, Н1.2); как запасной вариант для редких разделов допустимо с ссылками на важное на главной (по NN/g).

Связь со слабым местом № 4 из R-1.2: главная — не архив, а вход в сценарии; Н1.7 показывает, что внимание держалось в верхней трети экрана, поэтому главное на «Сегодня» стоит в верхней части, а действие, которое делают одной рукой, — в нижней (П2). **Проверять эту гипотезу надо пробой на однокурсниках — это пакет 4.5 плана, требование ЗД-2; в источниках она не подтверждена.**

Рекомендации по раскладке здесь нет: она выбирается на макете в пакете 2.1.

### 4.2. Порог зоны касания (развилка для дизайн-системы 2.2)

- **Вариант 1:** 44×44 CSS px для всех кнопок, вкладок и полей, кроме ссылок внутри текста. Совпадает с Apple по умолчанию и с WCAG 2.5.5; выше минимума AA с запасом.
- **Вариант 2:** 48×48 и 8 px зазора. Совпадает с Material/Android и web.dev; дороже по месту на 360 px.
- **Вариант 3:** 24×24 как проходной порог автотеста (соответствие AA) и 44 для основных действий. Проще, но слабее для движения на ходу.
- Замечание «Стек» (Н2.8): основные варианты кнопок shadcn/ui из коробки — 32–40 px, под варианты 1 и 2 размеры надо задать самим. У вариантов `xs` и `icon-xs` высота 24 px — ровно граница критерия 2.5.8: при варианте 3 они проходят автотест без запаса.

**Рекомендация (решает участник А в пакете 2.2, после Р-3).** Вариант 1 с одним уточнением: **44×44 CSS px — норма дизайн-системы** для кнопок, вкладок и полей; **24×24 — нижняя граница автотеста**, ниже которой элемент не проходит уровень AA. Доводы:
1. 44 — размер Apple по умолчанию (Н2.3) и порог критерия WCAG 2.5.5 (Н2.2).
2. Из трёх чисел только 44 есть в ГОСТ Р 52872-2019: критерий 2.5.5, уровень AAA, «по меньшей мере 44x44 пикселя CSS». Критерия 2.5.8 с числом 24 в ГОСТ нет (Н9.3; текст копии на сайте Тифлоцентра открыт 11.11.2026). Если описание проекта ссылается на ГОСТ, опереться можно только на 44.
3. 48 (вариант 2) — число из руководств Android и web.dev, в WCAG и в ГОСТ его нет; на 360 px оно дороже по месту.

Оговорка: 2.5.5 — уровень AAA. Обязательным число 44 делает не стандарт, а решение проекта; по уровню AA обязательны только 24 px.

### 4.3. Что дёшево автоматизировать, что нет

Автотестом на Playwright 360×800 берутся: размеры целей (П3–П4), отсутствие горизонтальной прокрутки (П7), контраст в двух темах (П9, П32), метки полей и `autocomplete` (П18), статус-области (П20, П27), состояния при задержке/офлайне (П22, П25), «меньше движения» (П31), отсутствие запроса разрешений (П28), число касаний (П17). Нужны ручные проверки на телефоне: П2, П5 (iOS), П8, П10 (снимок), П14 (понятность), П21 (понятность), озвучивание, слабая сеть, скорость на реальном устройстве. Для 4.3 «Скорость и доступность» из этого получаются числа: LCP, CLS, TBT из Lighthouse; число нарушений axe; размеры целей; число касаний.

### 4.4. Расписание (слабое место № 5)

Вариант «минимум»: список по дням, метка недели, статусы пар текстом + зачёркивание (П10–П13). Вариант «плюс»: подписка на календарь и виджет — спрос подтверждён отзывами других вузов (R-1.2, раздел 4), но это функции 2.x, а не приёмы интерфейса, и в этом отчёте не оцениваются.

### 4.5. Заявки и статус (слабое место № 6)

Компонент USWDS описывает шаги заполнения формы, а не готовность заявки. Открытых образцов «отслеживания заявки» по шагам я не нашёл (R-1.2: «не найдено»), поэтому П21 опирается на разметку этого компонента (по аналогии — предположение) и на жалобы из R-1.2. Сроки и ответственного в шагах источники не описывают; это решение дизайнера.

### 4.6. Состояния и «не работает» (слабое место № 1)

Приёмы П22–П25 закрывают видимую часть: что видит студент при задержке, пустоте и сбое. Они не лечат нестабильность самого сервера — это работа по 3.7 и 4.x. Из жалоб на ИТМО и ДВФУ (Н7.8) следует проверить именно «серый экран» и «бесконечную загрузку»: в тестах задержка 12 с и ответ 500 обязательны.

### 4.7. Связанное с Р-2 и Р-3

- **Р-2 (концепция).** Все 36 приёмов не зависят от выбранной концепции. Для варианта 1 «Деканат приходит сам» особенно нужны П12, П21, П26–П28; для варианта 3 «Семестр как маршрут» — П14–П16.
- **Р-3 (стек).** Приёмы от стека не зависят. Строки «Стек»: Н2.8 (размеры кнопок shadcn/ui), Н7.9 (`loading.js` и потоковая выдача в Next.js, статус 200 у страницы «не найдено»), Н9.12 (варианты Tailwind для движения, темы и сенсорного ввода), Н11.7 (версии Node для инструментов).

## 5. Что не найдено и что осталось под сомнением

**Не найдено:**
- Норматив о том, где на экране держать главное действие одной рукой (раздел 2.1).
- Первоисточник наблюдения из Н1.5 — статья в UXmatters (ошибка 522): число 49 % взято из сводки поиска.
- Страница Material Design 3 о нижней панели (`m3.material.io`) скриптом не открылась; использованы документы репозитория Material Components Android.
- Минимальный размер шрифта в WCAG (не нашёл; полный перебор стандарта не делал — **предположение**, что такого критерия нет).
- Первоисточник Apple о масштабировании при фокусе в поле ввода (только вторичные тексты).
- Исследований «заметность переносов и отмен в расписании» и открытых руководств по их оформлению: нашёл только трекер стороннего приложения (Н4.2). Официальная справка Untis вернула 403.
- Открытый образец отслеживания заявки по шагам, а также статья NN/g про индикаторы хода (404).
- Веб-руководство web.dev по запросу разрешения на push (404).
- Скорость мобильной сети в России по официальному источнику.
- Разумный вес страницы для мобильной сети в виде числа с датой и источником: найдены только медианы мира (Web Almanac 2025) и старый ориентир web.dev без даты.
- Хорошее пороговое значение TBT (в прочитанных страницах нет).
- Юридически обязательный уровень (A/AA/AAA) для кабинета вуза (Н9.4).
- Таблица соответствия критериев ГОСТ Р 52872-2019 пунктам WCAG 2.1: прочитана только первая часть копии (около 100 тыс. из 168 тыс. знаков).
- Официальные Apple и Android страницы, подтверждающие, что 44 pt/48 dp равны CSS px в вебе (предположение).

**Под сомнением:**
- Все числа и формулировки прошли через пересказ инструмента чтения; критерии WCAG сверять по ссылкам из таблиц, особенно 2.5.8 (исключение «расстояние»), 1.4.12, 3.3.3 и 3.3.4 (уровни не сверены).
- Исследование NN/g о скрытой навигации — 2016 год, коммерческие сайты; применимость к кабинету студента — предположение. Статьи NN/g 2015 и 2017 годов — тоже старые.
- Утверждение, что Lighthouse 12 заменил «tap-targets» на `target-size`, получено из сводки поиска с цитатами заметок о выпуске.
- Правила Apple HIG о разрешениях и уведомлениях написаны для приложений; перенос на веб — по аналогии.
- Автоматические проверки в таблице у 28 приёмов из 36 — целиком сценарии, придуманные автором; в источниках их нет. На правила axe из документации опираются П6, П9, П18, П32 и частично П3 и П15; на метрики Lighthouse — частично П23 и П36. Отметка стоит у каждого приёма в колонке «Как проверить». Ни один способ не запускался: команд оболочки у роли нет, инструменты проверены только по реестру npm и страницам проектов.
- Лицензия MPL-2.0: объяснение условий — общее знание, текст лицензии не читал.
- Страницы web.dev о бюджетах, тёмной теме и целях касания не датированы.
