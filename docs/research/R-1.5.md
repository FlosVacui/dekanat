# R-1.5. Типовые ошибки безопасности веб-кабинетов: список проверок

Дата работы: 11.11.2026. Все «дата обращения» ниже — 11.11.2026. Исполнитель: researcher (Sonnet 5.5 / high). Задание: [B-1.5](../briefs/B-1.5-security.md).

Как читать надёжность источника:
- **высокая** — официальная документация, первоисточник стандарта или сервиса;
- **средняя** — OWASP/NIST/PostgreSQL, прочитанные через пересказ инструмента (слово в слово я их не видел), либо документация сторонней библиотеки;
- **низкая** — форум, база знаний вендора, сводка поиска, новость без первоисточника.

Как читались страницы: инструмент пересказывает страницу. Документацию Next.js он отдал почти целиком (текст страницы виден), поэтому по ней надёжность «высокая». Страницы OWASP и NIST пересказаны: цитат в отчёте нет, только смысл и числа. Чужие сайты и настоящие кабинеты вузов не проверялись, запросов на чужие системы не отправлялось. На прочитанных страницах просьб что-то сделать не было.

Важное допущение. Рекомендуемый стек (Р-3) ещё не утверждён. Библиотека входа не выбрана. Где я привожу пример библиотеки (Better Auth), это пример для сравнения, а не рекомендация.

## 1. Вопросы и короткие ответы

1. **Чужие данные по адресу.** Это ошибка «нет проверки владельца»: сервер берёт номер из адреса или тела запроса и отдаёт запись, не проверив, что она принадлежит вошедшему. OWASP ставит её на первое место в API Top 10 (API1:2023, BOLA) и в Top 10:2025 на A01 (Broken Access Control). Тест: два студента, у каждого своя запись с уникальной меткой; студент А запрашивает запись Б всеми способами (страница, API, Server Action, изменение, удаление). Провал — любой ответ с данными Б или изменение записи Б. Статус 403 и 404 оба допустимы. Сверка «id из сессии равен id из адреса» одна не спасает: OWASP прямо пишет, что она закрывает лишь часть случаев (см. F1–F4).
2. **Вход и сессии.** Хеш пароля: OWASP предпочитает Argon2id, минимум 19 МиБ памяти, 2 прохода, параллелизм 1; запасной scrypt (N=2^17, r=8, p=1), для старых систем bcrypt с коэффициентом не менее 10 и пределом 72 байта. NIST SP 800-63B-4: пароль как единственный фактор — минимум 15 символов, максимум допускать не менее 64, правил состава не требовать, периодической смены не требовать, чёрный список обязателен, не более 100 неудачных попыток подряд на одну учётную запись. Куки сессии: HttpOnly, Secure, SameSite задан явно, без Domain, по возможности с префиксом `__Host-`; выход обязан гасить сессию на сервере. От подделки запросов: Server Actions в Next.js принимают только POST и сверяют Origin с Host; для обычных Route Handler защиты в документации не найдено — проверка вручную. Что даёт стек, что делается руками — раздел 3 (F5–F22).
3. **Ввод и вывод.** XSS: React экранирует вывод сам; опасны `dangerouslySetInnerHTML`, `innerHTML`, ссылки из ввода пользователя, вывод модели. SQL-инъекция: параметризованные запросы; части запроса, которые нельзя параметризовать (имя столбца сортировки), — только по списку разрешённых. В кабинете это текст заявки, тема, сообщения, ФИО (его видит сотрудник), поиск, параметр сортировки, имя файла, поле «ссылка». Проверка: полезные нагрузки из тестового набора в каждое поле + поиск опасных конструкций в коде. Загрузка файлов, если появится: список расширений, лимит размера, случайное имя, хранение вне публичной папки, проверка прав при скачивании (F23–F29).
4. **Секреты.** Любая переменная с префиксом `NEXT_PUBLIC_` вшивается в JavaScript для браузера при сборке. Ключ `env` в `next.config.js` вшивается всегда. Типовые ошибки: секрет с таким префиксом; секрет в `env`; весь объект из базы передан в клиентский компонент; включены карты исходного кода; `.env` попал в git или образ Docker. Проверка: gitleaks по истории, поиск имён и значений секретов в `.next/static` и в HTML (F30–F37).
5. **Заголовки и HTTPS.** Основа по OWASP: Strict-Transport-Security, Content-Security-Policy, X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy, защита от встраивания (frame-ancestors или X-Frame-Options), Cache-Control: no-store для личных страниц; убрать X-Powered-By. Бесплатно и без регистрации: MDN HTTP Observatory (проверяет любой публичный домен, регистрация в документации не упомянута), Qualys SSL Labs (форма с именем хоста), `curl -I`, тест Playwright. Все три внешних сервиса видят только публичный адрес, на localhost их не применить (F38–F44).
6. **Ошибки и журналы.** Пользователю — общий текст без трассировки, SQL, путей, версий. В журнал не писать пароли, токены, идентификаторы сессий, ключи, строки подключения к базе, персональные данные. Писать: неудачные входы, отказы в доступе, ошибки (F45–F49).
7. **Тестовые аккаунты для жюри.** Публичный пароль превращает кабинет в место, куда может войти кто угодно: нужны запрет смены пароля и контактов, сброс данных, роли без лишних прав, лимиты на запись и расход, отдельная база без чужих ключей. Хороших первоисточников по этому пункту не найдено; рекомендации ниже — перенос принципов OWASP и сводки поиска, они помечены «предположение» (F50–F54).
8. **ИИ-помощник (Р-5).** OWASP Top 10 для приложений с языковыми моделями (2025): LLM01 внедрение инструкций, LLM02 раскрытие чувствительных данных, LLM05 небезопасная обработка вывода, LLM07 утечка системного запроса, LLM10 неограниченный расход. Защиты в самой модели нет; OWASP советует проверки на стороне кода: права из сессии, а не из подсказки; вывод модели — как недоверенный ввод; лимиты и квоты (F55–F62).
9. **Зависимости.** `npm audit` (нужен доступ к реестру npm и файл `package-lock.json`), OSV-Scanner (Google), `gitleaks` для секретов. Для Next.js в 2026 году действует формальный график выпусков безопасности: последний — 03.11.2026 (v16.4.5 и v15.5.29). Что делать с найденным — раздел 3 и таблица Д (F63–F68).
10. **Сводная таблица.** Раздел 4: 64 проверки, десять обязательных помечены ★ и перечислены в 4.10.

## 4. Сводная таблица проверок

Обозначения. «Авто»: **П** — тест Playwright; **З** — запрос (curl/`request` Playwright) или скрипт; **К** — команда или поиск по коду; **Р** — вручную. «Тт» — требование матрицы (ЯД-1, ЗД-5, ТР-9.2, ТР-9.3, КО-3). ★ — одна из десяти обязательных (номер в скобках).

Общая подготовка для тестов доступа: два вымышленных студента А и Б; у каждого в данных уникальная метка (например, `МЕТКА-А-…`) в заявке, оценках и профиле; тест ищет метку другого в теле ответа. Статус сам по себе не доказательство: ответ 200 без метки допустим, ответ 403/404 допустим, ответ с меткой — провал.

## 5. Что это значит для проекта

Решения принимают оркестратор и пользователь. Ниже — варианты.

**Вход и сессии (пакет 2.3).**
- Вариант А: готовая библиотека входа. Плюс: хеш, куки, проверка Origin и лимит запросов часто уже есть (пример: F69, F70). Минус: у каждой библиотеки умолчания свои, их нужно читать и проверять тестами В-01…В-10; для Auth.js и других поведение я не проверял.
- Вариант Б: свой вход по документации Next.js. Плюс: полный контроль. Минус: пример в документации слабее требований (F15) и не даёт выхода с гашением сессии без доработки (F21).
- Сессия на сервере (таблица в PostgreSQL) делает проверки В-07, В-09 выполнимыми; сессия только в подписанной куке не позволяет принудительно закрыть вход. Это следует из описания в документации Next.js (F15), поэтому для «выход гасит сессию» вариант с таблицей проще.
- Срок сессии — выбор проекта: короткий срок безопаснее (F20), но студенты жалуются на слетающий вход (R-1.2). Возможный компромисс — длинный абсолютный срок и простой, и повторный ввод пароля для чувствительных действий (смена пароля, телефона). Это идея, не проверенная источниками.

**Доступ к данным.**
- Слой доступа к данным (DAL) с проверкой владельца в каждом запросе, как советует Next.js (F7), и тесты П-01…П-04 по матрице «роль — адрес — метод» (F4). Предлагается одна точка, где данные запрашиваются, чтобы аудитор (пакеты 2.6, 4.4) мог проверить её целиком.
- RLS в PostgreSQL: даёт вторую линию защиты, но требует отдельной роли БД, политик и тестов (F12). Для прототипа — вариант «по желанию».
- `use cache` и `unstable_cache` для личных данных не использовать — после выпуска 03.11.2026 это зафиксировано как источник утечек (F10).

**Тестовые аккаунты (КО-3, СД-1).**
- Публичный пароль неизбежен (F52). Варианты снижения: серверный запрет смены пароля и контактов; ночной сброс данных + кнопка сброса, доступная только тестовым учёткам; лимит записей в сутки; роли студент/сотрудник без публичной админской учётки; отдельная база и сервер без чужих ключей (F54). Источников первого порядка здесь нет — это перенос принципов, пометка «предположение».
- Если Р-5 принят, лимит запросов к ИИ на тестовую учётку отдельный и жёсткий (F61, И-02).

**ИИ-помощник (Р-5).**
- Узкий срез «ответ по базе правил» безопаснее свободного чата, потому что косвенного канала внедрения нет, пока в корпус не попадает пользовательский текст (И-05). Это вывод из F56, не проверенный на нашем коде.
- Права и выбор данных делает код по сессии (F59); модель получает только текст правил и вопрос.
- Лимиты и «контрольные метки» делают атаки проверяемыми (F57, F61).

**Проверки в процессе.**
- Часть проверок (gitleaks, `npm audit`, OSV, поиск опасных конструкций, поиск меток) можно запускать как команды; вопрос, добавлять ли их в `tools/check_all.py` или отдельный скрипт, оставляю оркестратору: этот файл я не читал.
- Внешние сканеры заголовков и TLS работают только по публичному адресу, значит, после развёртывания (пакет 2.5); до того заголовки проверяет Playwright (F44).

**Версии.** Next.js выпускает исправления безопасности ежемесячно и внепланово (F65). Нужно решить, когда закрепить версию: предлагаю проверять на воротах 3, на воротах 5 и перед сдачей (это предложение, не решение).
