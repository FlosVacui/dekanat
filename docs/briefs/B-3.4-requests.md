## Что сделать

### 1. Поля заявки — логика и база
1. В `app/src/lib/requests.ts`:
   - **Справка из деканата** — поле «Куда справка», 17 значений из таблицы 3.2 отчёта R-1.6, в том же порядке. Слова — как в таблице, первая буква прописная: «В паспортный стол», «В страховую компанию» и так далее; «в ВУЗ» пиши «В вуз». Значение по умолчанию — «По месту требования». В базе хранится ключ латиницей, не русский текст. В комментарии к списку напиши дословно: «Перечень со страницы faq.gubkin.ru, прочитан 12.11.2026. Со списком в кабинете вуза человеком не сверен».
   - **Справка об оплате обучения** — поле «Год оплаты»: годы от 2024 до текущего года включительно; текущий год берётся по часовому поясу из настроек, как остальные даты. По умолчанию — прошлый год, но не раньше 2024. Основание: «налоговый период не ранее 2024 года», R-1.6, строка 84. Значение по умолчанию — решение проекта.
   - **Заявление на материальную помощь** — полей нет.
   - Функции проверки значения и значения по умолчанию — чистые, с тестами.
2. База: новая миграция. Два столбца в `requests`, оба допускают пустое значение: назначение справки и год. Ограничения в базе, как у `kind` и `status`: назначение — только из списка; год — не меньше 2024; назначение заполнено только у справки из деканата, год — только у справки об оплате, у материальной помощи оба пустые. Существующие строки миграция заполняет значениями по умолчанию, иначе ограничение не встанет. Миграцию создаёшь командой `npm run db:generate`, существующие файлы миграций не правишь.
3. `createMyRequest` принимает значения полей. Чужое или несуществующее значение сервер не принимает: заявка не создаётся. Значение для вида, у которого поля нет, отбрасывается. Проверка — в слое доступа, не только на странице.
4. `RequestItem` отдаёт новые поля; `getCohortRequest` для сотрудника — тоже.

### 2. Э-7 «Новая заявка»
1. Под карточкой с видом и сроком — поле своего вида: настоящий `<select>` с видимой подписью `<label>`. Значение по умолчанию выбрано. У материальной помощи поля нет.
2. Три касания сохраняются: вкладка «Заявки» → кнопка вида → «Отправить». Сквозной тест `m0.spec.ts` должен остаться зелёным без правки шагов подачи.
3. Значение не из списка в форме — заявка не создаётся, переход на `/requests`, как сейчас при неизвестном виде.
4. **«Подать снова» с прежними значениями.** Адрес — `/requests/new?type=<вид>&from=<номер заявки>`. Страница читает прежнюю заявку только через `getMyRequest(actor, from)`: владельца берёт сервер из сессии. Заявки нет или она чужая — `denyRecord(actor)`, как на Э-8. Вид прежней заявки не совпал с `type` — переход на `/requests`. Прежнее значение подставляется в поле; если оно больше не подходит, например год вне диапазона, — значение по умолчанию. Значения полей в адрес не кладутся.

### 3. Э-8 «Заявка» — состав и тексты
Порядок частей сверху вниз — D-2.2-system, подраздел 5.12; правила шагов и таблица «Шаги по статусам» — 5.8; блок — 5.9; ссылка — 5.10. Оформление — нынешними утилитами Tailwind, как на остальных экранах продукта.
1. Первой — ссылка «Все заявки» на `/requests`. Высота зоны касания не меньше 44 пикселей.
2. Заголовок с видом заявки и подписью «Подана <дата>» — как сейчас. Под подписью — строка поля: «Куда: <значение>» или «Год оплаты: <год>»; у материальной помощи строки нет.
3. Статус словом. `data-testid="request-status"` остаётся и содержит ровно слово статуса: на него опираются тесты. Плашку с цветом и значком не делаешь.
4. Блок «Что сделать вам»: `<section>` с заголовком `<h2>`, связанным через `aria-labelledby`. Текст — `statusText()`; `data-testid="request-status-text"` переезжает на текст блока. При «Выдана» блока нет. Нынешняя карточка «Сейчас» убирается.
5. Примечание `request.note`, если оно есть, — строкой под блоком, над шагами; при «Выдана» — на том же месте.
6. Шаги: `<ol aria-label="Шаги заявки">`. В каждом шаге по порядку: слово состояния, название, пояснение. Слова состояния — «СДЕЛАНО», «СЕЙЧАС», «ДАЛЬШЕ», «ДАЛЬШЕ — ВАМ», «ОТКЛОНЕНО», прописными в разметке. Состояния и пояснения для всех сочетаний статуса и вида — таблица «Шаги по статусам» и таблица «Откуда берутся поля шага» в 5.8. Коротко:
   - пояснение пройденного шага — день и время события: `formatDate(todayIn(timezone, createdAt))` и `nowTimeIn(timezone, createdAt)`; у шага «Подана» после времени — слова «Деканат её получил.»;
   - «В работе», когда он текущий: «Срок — до <dueDate>.»;
   - блок «Куда» и «До какого дня» стоит на шаге «Готова» только при статусе «Готова»;
   - **выдана:** все четыре шага «сделано», `aria-current` нет ни у одного;
   - **отклонена:** остаются только шаги, у которых есть запись в `events`; следом один шаг «Отклонена» со словом «ОТКЛОНЕНО» и `aria-current="step"`. Непройденных шагов нет.
7. Кнопки внизу. У отклонённой — «Подать снова» (адрес из шага 2.4) и под ней «К списку заявок». У остальных — что сказано в таблице «Пять видов» подраздела 5.12.
8. Набор шагов и их состояний собирает **чистая функция** в `app/src/lib/requests.ts`: на входе вид, статус, события и даты заявки, на выходе список шагов с состоянием и пояснением. Страница только рисует. Перенос дизайн-системы потом поменяет вид, а не логику.

### 4. Тексты — что меняется в `statusText()`

- Срок «получите до <дата>» у справок остаётся вымышленным: день «Готова» плюс срок изготовления вида. Источника срока получения нет; комментарий у `computePickupUntil` оставь.

## Ловушки
- **Путь к репозиторию содержит кириллицу и пробелы.** В командах оболочки — полный путь в кавычках.
- **Локальная база останавливается сама.** Программы — в `%LOCALAPPDATA%\dekanat-pg\pgsql\bin`, в `PATH` их нет. Перед каждым прогоном: `pg_isready -h 127.0.0.1 -p 5432`. Не отвечает — запусти отдельным процессом через `Start-Process` в PowerShell: `pg_ctl -D <папка данных> -l <файл журнала> -o "-p 5432 -c listen_addresses=127.0.0.1" start`. Фоновой задачей не запускай: база зависает. Базу не останавливай, папку данных не удаляй.
- **Без базы общая проверка пропускает два шага продукта, а код возврата нулевой.** Читай итог, а не код: строк «пропущено» быть не должно.
- **Сквозной тест нестабилен:** процессы браузера или сервера иногда падают с кодом `0xc0000005` или `3221225477`, причина не установлена. Красный прогон из-за падения процесса повтори один раз и напиши об этом в отчёте. Красный из-за проверки теста — это твоя ошибка, ищи её.
- **Порт 3100 и база общие** с другими сессиями на машине. Сервер разработки не оставляй запущенным; свои процессы останови перед отчётом.
- **Next.js 16:** `params` и `searchParams` — `Promise`; серверные действия — в файлах с `'use server'`. Образцы — нынешние страницы заявок.
- **Миграция и существующие строки:** сначала столбцы и заполнение, потом ограничение. Проверь `npm run db:migrate` на базе, где заявки уже есть, и `npm run db:seed` после.
- **Роль базы у приложения ограничена:** `app/tests/unit/db-role-and-boundaries.test.ts`. Новые столбцы должны читаться и писаться под ней.
- **Сканер секретов** может принять тестовые пароли за находку. Шаг gitleaks покраснел — правило не отключай, верни в отчёте.
- Ширины 360 пикселей хватает не всему: длинные значения «Куда справка» переносятся, а не обрезаются. Последний пункт перечня длинный — проверь его на 360 и 320.
