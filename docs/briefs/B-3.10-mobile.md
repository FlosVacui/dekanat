## Цель
Ворота 3 закрывают ядро кабинета целиком. Нужно узнать, работают ли основные сценарии студента и сотрудника на экране телефона шириной 360 и 390 px: ничего не обрезано, нет прокрутки вбок, кнопки достаточно велики, главное видно. Требования — ЗД-4 «полноценная работа на телефоне» и КО-3 в `docs/REQUIREMENTS.md`. На воротах 2 такой проверки не было: её перенесли сюда.

## Что сделать
**Промежуточный итог — после каждого пункта и после последнего прогона:** две-три строки в `%LOCALAPPDATA%\dekanat-runs\mob-3.10-progress.md`, файл перезаписывай целиком.

1. **Новый файл теста** `app/tests/e2e/mobile-m1.spec.ts`: проходит сценарии на 360×800 и 390×844, для сравнения — на 1280 px. Студент: С-1, С-2, С-3, С-5, С-6, С-7, С-9, С-10, С-12, С-14, С-15, С-16 и экран дисциплины. Сотрудник: список заявок и экран заявки — **без нажатия «Сохранить»**.
2. **Файл только читает.** Он не подаёт заявок, не меняет статус, не отмечает уведомления прочитанными и не выходит из чужой сессии: сквозные тесты зависят от порядка файлов, и `m0.spec.ts` уже меняет ленту перед `notifications.spec.ts`. Подача заявки и смена статуса на 360 px уже проверены в `m0.spec.ts` и `requests.spec.ts` — сошлись на них. Сценарий С-8 и С-13 — по этим тестам и по снимкам, а не своим нажатием.
3. **На каждом экране и в каждой ширине** тест проверяет:
   - нет прокрутки вбок: ширина документа не больше ширины окна;
   - все кнопки, ссылки, вкладки, поля — не меньше 24×24 px; список тех, что меньше 44×44, — в отчёт, с размером;
   - нет наложения шапки и нижней панели на содержимое при прокрутке до конца;
   - главное действие экрана видно без прокрутки или назови, где оно.
   Проверки — точным шаблоном, не подстрокой: ошибка ИИ 125.
4. **Снимки** каждого шага в 360 и 1280 px — в `docs/evidence/screenshots/2026-11-17-3.10/`. Имя файла говорит, что на снимке: `360-grades-session.png`. Неудачный снимок получает `fail-` в начале и не удаляется. Чужие папки снимков не перезаписывай, скрипты `screenshots.ts` и `screenshots-requests.ts` не запускай.
5. **Доступность.** Подписи полей на входе; порядок фокуса клавишей Tab на «Сегодня», в заявке и у сотрудника — по шагам; правило axe `target-size` и контраст, если `@axe-core/playwright` уже стоит в `app/package.json`. Не стоит — проверь вручную по снимкам и скажи «axe нет». Ставить пакеты нельзя.
6. **Скорость.** Время до появления главного блока на «Сегодня», «Расписании», «Успеваемости» на 360 px — замером в тесте, три прогона, числа в отчёт как есть. Сеть не замедляй.
7. **Пометка «концепт для конкурса»** видна на входе и в подвале — проверь на 360 px.
8. **Состояния «пусто, ошибка, загрузка».** Сам ошибку не вызывай: отзыв права в базе — чужой приём. Оцени состояния по снимкам `2026-11-16-3.7/` и по `app/tests/e2e/states.spec.ts`: какие экраны на 360 px сняты, каких снимков нет.
9. **Прогон.** С привязкой к ядрам, см. «Ловушки»: сначала свой файл одним прогоном сразу после `npm run db:seed`; затем `npm run test:e2e` целиком — новый файл не должен ломать чужие тесты. Время с часов в начале и конце каждого прогона — в отчёт. Общую проверку `tools/check_all.py` не запускай.
10. **Отчёт** `docs/reviews/MOB-3.10.md`. Номера замечаний — `R-3.10-101`, `R-3.10-102` и дальше: номера с 1 занимает аудит безопасности тех же ворот; другой вид номера команда учёта не примет — ошибка ИИ 103. Серьёзность: блокирующее, существенное, незначительное, предложение. Каждое замечание — со снимком или шагами. Колонку «Решение оркестратора» оставь пустой. Отдельным разделом — что должен проверить человек на настоящем телефоне.

Не хватает лимита — порядок: 1–4 и 9 для студента, затем сотрудник, затем 5–8. Что не успел — поимённо в «Что не проверялось».

## Ловушки
- **Файлы пишутся только инструментами записи и правки.** Heredoc нельзя — ни для файлов, ни для `python`, ни для `node`: скрипт — файлом в `%LOCALAPPDATA%\dekanat-runs\`, запуск оттуда — ошибка ИИ 104.
- **Команду с `cd` бери в скобки:** `(cd app && ...)`.
- **Машина нестабильна:** процессы Node.js падают с кодами `3221225477` и `3221225622`. Команды `npm`, `npx`, `node` — только так, из Git Bash: `(cd app && cmd //c "start /b /wait /affinity FFFF0000 npx playwright test tests/e2e/mobile-m1.spec.ts")`. `cmd start` не передаёт код возврата: итог читай по строкам `passed` и `failed`. Упал процесс с таким кодом или Chromium с «Page crashed» без проваленных по существу проверок — повтори один раз и назови оба результата.
- **Локальная база** — `127.0.0.1:5432`. Перед прогоном: полный путь `%LOCALAPPDATA%\dekanat-pg\pgsql\bin\pg_isready -h 127.0.0.1 -p 5432`, смотри код возврата. Не отвечает — не чини, верни в ответе.
- **Красные все тесты подряд** — проверь право чтения таблиц: прежний тест `states.spec.ts` отзывает его на время. Право возвращает `npm run db:migrate`, а не `npm run db:seed`. Перед отчётом — `npm run db:seed`.
- **День недели.** Красный `schedule.spec.ts` или `grades.spec.ts` — сначала R-3.2-1 в [RV-3.2-1](../reviews/RV-3.2-1.md) и пункт 9 [RV-3.3-1](../reviews/RV-3.3-1.md). Твой файл не должен зависеть от дня недели: в день без пар экран расписания пуст — это не ошибка.
- **Время бери с часов:** `TZ='<+03>-3' date`. В шапке отчёта — с часов, не по памяти: ошибки ИИ 101 и 129. Между 23:50 и 00:05 МСК сквозные тесты не запускай.
- **`.env` не читать.** Сервер для тестов — помощники `app/tests/e2e/helpers/server.ts`.
- **Проверка чистоты** `tools/check_clean.py`: в отчёте не пиши абсолютных путей этой машины и записей вида «пакет@версия». На снимках — только вымышленные данные.
- Путь к репозиторию содержит кириллицу и пробелы. Кириллица в `-g` через `cmd` может не найти тесты: перед запуском — `chcp 65001`.
- **Перед отчётом проверь, что твоих процессов не осталось:** `node`, `next`, `playwright`, `chromium`, `bash`, `python` с папкой проекта или `dekanat-runs` в командной строке. Останови только свои. Чужие `node` и `chrome` не трогай: на машине идёт другой проект.
