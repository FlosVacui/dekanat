## Итог
**Доработать.** Слой доступа, хеш, сессия на сервере и правила для секретов в целом верны и следуют из источников. Одно блокирующее: аккаунт сотрудника с публичным паролем меняет статус любой заявки всех студентов, включая резервный набор. Поэтому резервные аккаунты, о которых просил пользователь, не защищают главный сценарий ЯД-4. Восемь существенных. Большая часть касается тех же публичных аккаунтов: параллельный залп обходит счётчики; обход прокси через прямой порт; лимит записи как способ отказа в обслуживании; подбор пароля резервных аккаунтов не ограничен. Ещё два ложных утверждения о проверках и о задании, а также сроки П-05 и П-12.

## Шаг 3. Вход и сессии (ADR-0003): по порядку
- **Параметры хеша.** N=2^16, r=8, p=2 — вторая строка таблицы scrypt (F13, `R-1.5:62`; В-01, `:220`). Умолчания `crypto.scrypt` ниже порога (F16) — учтено. Пропущен `maxmem` — R-2.3-10.
- **Расчёт памяти.** 64 МиБ верно. Довод «лимит по адресу до хеша» не ограничивает одновременность для многих адресов и для верных входов — R-2.3-4.
- **Токен.** 32 байта от криптографического генератора, в базе SHA-256 — выше порога F19 (128 бит). В порядке.
- **Флаги куки.** HttpOnly, Secure, SameSite=Lax, Path=/, без Domain, срок задан — как в F19 и В-06. Префикс `__Host-` — R-2.3-21.
- **Срок.** 7 суток против F20: дольше простоя по OWASP, короче 30 суток по NIST AAL1. Источник передан верно. Вход только по паролю — это AAL1 по определению, так что опора на AAL1 законна.
- **Выход.** Удаляет строку сессии — закрывает F21. В порядке.
- **Одинаковые ответы.** Текст, код и время одинаковы. Дыра через поведение счётчика — R-2.3-11.
- **Три счётчика.**
  - Закрыть вход жюри посторонний не может, если сидит на другом адресе. Может, если сидит за общим адресом — автор это назвал.
  - Новые пути отказа в обслуживании: лимит записи и верные входы — R-2.3-4.
  - Обход сменой заголовка закрыт, только если до приложения нельзя дойти мимо прокси — R-2.3-3.
  - Обход параллельным залпом — R-2.3-2. Обход сменой адреса для резервных — R-2.3-5.
  - Числа между собой не спорят. На одной паре 20 попыток набегают примерно за 38 минут: 5 без ожидания, потом ожидания 1+2+4+…+256 (511 секунд) и шесть раз по 300 секунд — 2311 секунд. Значит, на одном аккаунте раньше срабатывает пара, а лимит по адресу — на многих аккаунтах.
  - С границей NIST расходится только строка «без `is_demo`» (пауза вместо отключения); исключение для `is_demo` не записано — R-2.3-5.
- **Резервные аккаунты.** Решение пользователя записано верно, но от порчи через сотрудника не защищает (R-2.3-1), а подбор их паролей не ограничен (R-2.3-5).
- **Лимит записи** — сам становится способом атаки: R-2.3-4.
- **Отказ от ночного сброса.** Довод верен (критерий «данные сохраняются»). Но ручной сброс стирает то же самое — R-2.3-4 (в).

**Сценарии атаки, которых решения не закрывают:** порча всех заявок через публичного сотрудника (R-2.3-1); параллельный залп входов (R-2.3-2); прямой порт приложения с поддельным заголовком (R-2.3-3); исчерпание лимита заявок и поток верных входов (R-2.3-4); подбор пароля резервного аккаунта со сменой адреса (R-2.3-5).
