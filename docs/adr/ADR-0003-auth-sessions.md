| Связано | ЯД-1, ЗД-5, ТР-9.2, ТР-11, СД-1; [ADR-0002](ADR-0002-data-access.md), [ADR-0004](ADR-0004-secrets-config.md); проверки В-01…В-12, Т-01…Т-07 из [R-1.5](../research/R-1.5.md), разделы 4.2 и 4.7 |

## Контекст
- Задание: вход по логину и паролю; пароли не хранятся в открытом виде; тестовые аккаунты с логинами и паролями — в комментарии к работе: ЯД-1, ТР-9.2, СД-1.
- Пароли тестовых аккаунтов публичны. Блокировка по числу попыток дала бы любому посетителю способ закрыть вход жюри: R-1.5, раздел 5.
- Студенты других вузов жалуются на слетающий вход; короткая сессия безопаснее: [сводка](../research/SUMMARY.md), ЯД-1.
- Next.js не даёт ни хеша, ни защиты от перебора, ни флагов куки. Пример входа из его документации слабее требований и не гасит сессию при выходе: R-1.5, раздел 3 и раздел 5.
- Числа OWASP и NIST в R-1.5 прочитаны в пересказе и человеком не сверены: R-1.5, раздел 6.

## Варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Готовая библиотека входа | Хеш, куки и лимиты часто уже есть | Умолчания у каждой свои; у Better Auth параметры хеша не названы, остальные не проверялись: R-1.5, раздел 6. Растущую задержку по паре «адрес и аккаунт» и запреты для тестовых аккаунтов всё равно писать самим |
| Б. Свой вход: таблица сессий в PostgreSQL | Полный контроль; каждое правило — свой тест; выход гасит сессию | Всё пишется руками; ошибку поймают только тесты и аудит |

## Решение
Вариант Б — решение проекта. Довод: правила для публичных тестовых аккаунтов нестандартны, и их всё равно пришлось бы писать поверх библиотеки, умолчания которой не проверены.

**Аккаунты.**
- Регистрации, смены пароля, смены контактов и сброса пароля в прототипе нет. Аккаунты создаёт скрипт вымышленных данных. Запросов на эти действия у сервера просто нет: проверка Т-01.
- Роли две: студент и сотрудник. Администратора нет.
- Все аккаунты прототипа — тестовые, с признаком `is_demo`.

**Пароль.**
- Хранится только хеш. Алгоритм — scrypt из стандартной библиотеки Node.js, параметры N = 2^16, r = 8, p = 2. Это один из допустимых наборов таблицы OWASP по R-1.5, проверка В-01.
- Умолчания `crypto.scrypt` ниже порога: параметры задаются явно. Соль случайная, своя у каждого пароля. В строке хеша записаны алгоритм и параметры — их можно усилить без смены схемы.
- Почему не Argon2id, первый в списке OWASP: стабильность `crypto.argon2` в Node.js в ресерче не найдена, а отдельный пакет — новая зависимость с непроверенной лицензией. Это решение проекта; при замене меняется одна функция.
- Проверка В-02 «политика пароля» не применяется: пользователь пароль не задаёт. Пароли основных тестовых аккаунтов публичны по заданию.

**Сессия.**
- После верного пароля сервер создаёт случайный токен — 32 байта от криптографического генератора. Токен уходит в куку; в базе лежит только его хеш SHA-256, номер пользователя, время создания и срок.
- Кука: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, без `Domain`, срок задан.
- Срок сессии — 7 суток от входа, без продления. Это выбор проекта: длиннее, чем OWASP советует для простоя, короче верхней границы NIST в 30 суток — R-1.5, находка F20. Довод: вход не должен слетать, а действий с высокой ценой ошибки в прототипе нет.
- Выход удаляет строку сессии. Каждый вход создаёт новый токен. Просроченная сессия не принимается.
- С одного аккаунта можно войти с нескольких устройств: один тестовый аккаунт откроют несколько членов жюри.
- Секретного ключа для подписи у сессий нет: токен случайный и проверяется по базе.

**Ответ на неверный вход.**
- Текст и код ответа одинаковы для «нет такого логина» и «неверный пароль». Для несуществующего логина хеш всё равно считается, чтобы время ответа не выдавало разницу: проверка В-05.
- Адрес возврата после входа — только внутренний путь: проверка В-12.

**Защита от перебора.** Числа — выбор проекта; источники дают границы.
| Счётчик | Правило | Зачем |
|---|---|---|
| Пара «адрес и аккаунт» | Пять неверных попыток — без задержки. Дальше ожидание удваивается: 1, 2, 4 секунды и так до 5 минут. Сбрасывается верным входом или через 15 минут тишины | Решение пользователя: задержка вместо блокировки. Посторонний замедляет только себя |
| Адрес | Не больше 20 неверных попыток за 10 минут по всем аккаунтам; дальше — ответ 429 до конца окна | Перебор по многим аккаунтам с одного адреса |
| Аккаунт без признака `is_demo` | Не больше 100 неверных попыток подряд; дальше — пауза на час | Верхняя граница NIST по R-1.5. В прототипе таких аккаунтов нет; правило проверяется на аккаунте, созданном тестом |

- Ожидание — это ответ 429 с временем до следующей попытки, а не удержание соединения.
- Счётчики лежат в базе, не в памяти приложения.
- Адрес посетителя берётся из заголовка, который ставит свой обратный прокси. Значение, присланное посетителем, прокси затирает: иначе счётчик сбрасывается подменой заголовка — проверка В-04.
- Лимит по адресу считается до вычисления хеша: хеш дорогой, и поток запросов иначе занял бы память сервера.

**Тестовые аккаунты.**
- Основной набор — два студента с разными данными и сотрудник: ТР-11. Их логины и пароли идут в комментарий к работе.
- Резервный набор — решение пользователя от 11.11.2026: такой же набор с другими логинами. Пароли резервных аккаунтов не публикуются и в git не лежат; задаются переменными окружения при создании данных. Если основной аккаунт испорчен, капитан заменяет комментарий к работе. Сколько резервных аккаунтов — решает пакет 3.8; не меньше одного набора.
- Лимит записи: не больше 20 заявок в сутки с одного аккаунта и ограничение длины полей. Число — выбор проекта.
- Автоматического ночного сброса данных нет: критерий жюри — «данные сохраняются», а сброс стёр бы заявку, поданную членом жюри накануне. Есть скрипт сброса, который команда запускает вручную при спаме. Это решение проекта.

**Подделка запросов.** Данные меняют только действия на сервере: Next.js сверяет для них Origin и Host. Поведение при отсутствии заголовка Origin в документации не описано — проверяется тестом В-10. Выход — тоже действие, а не ссылка.

## Последствия
- Что становится проще: каждое правило проверяется своим тестом; нет зависимости с непроверенными умолчаниями; нет секрета подписи.
- Что становится сложнее: код входа пишут ассистенты с нуля; ошибку в нём поймают только тесты В-01…В-12 и два аудита.
- Что нужно сделать: в пакете 2.4 — хеш, сессия, кука, выход; в пакете 3.1 — счётчики, одинаковые ответы, лимиты. На локальной машине без HTTPS флаг `Secure` мешает входу не во всех браузерах — способ локального запуска выбирает пакет 2.4, флаг на сервере не снимается.
- Слабые места:
  - Члены жюри за одним адресом сети делят лимит по адресу. Чужой перебор с того же адреса задержит и их.
  - Хеш scrypt с N = 2^16 занимает около 64 МБ памяти на одно вычисление — расчёт оркестратора по формуле 128 · N · r байт, на сервере не измерено. На 2 ГБ памяти одновременных входов немного; лимит по адресу стоит до хеша именно поэтому.
  - Семь суток жизни сессии на общем телефоне — риск; кнопка «Выйти» есть в профиле.

## Простыми словами
Пароль в базе не хранится: хранится его необратимый отпечаток, по которому пароль не восстановить. После входа сайт выдаёт телефону случайный пропуск на семь дней, а у себя записывает только отпечаток пропуска. Кнопка «Выйти» уничтожает пропуск на сервере. Если кто-то подбирает пароль, сайт заставляет его ждать всё дольше, но аккаунт не блокирует: пароли тестовых аккаунтов известны всем, и блокировка закрыла бы вход жюри. На случай порчи тестовых аккаунтов есть запасные.
