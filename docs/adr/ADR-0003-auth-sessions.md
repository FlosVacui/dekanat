# ADR-0003: вход, пароли, сессии, защита от перебора и тестовые аккаунты

| | |
|---|---|
| Статус | предложено |
| Дата | 11.11.2026; доработан 11.11.2026 по аудиту [RV-2.3-1](../reviews/RV-2.3-1.md) |
| Кто решил | Оркестратор. Решения пользователя от 11.11.2026: сброса пароля нет; для тестовых аккаунтов — растущая задержка и резервные аккаунты |
| Связано | ЯД-1, ЗД-5, ТР-9.2, ТР-11, СД-1; [ADR-0002](ADR-0002-data-access.md), [ADR-0004](ADR-0004-secrets-config.md); проверки В-01…В-12, Т-01…Т-07 из [R-1.5](../research/R-1.5.md), разделы 4.2 и 4.7 |

## Контекст
- Задание: вход по логину и паролю; пароли не хранятся в открытом виде; тестовые аккаунты с логинами и паролями — в комментарии к работе: ЯД-1, ТР-9.2, СД-1.
- Пароли тестовых аккаунтов публичны. Блокировка по числу попыток дала бы любому посетителю способ закрыть вход жюри: R-1.5, раздел 5.
- Публичен и пароль сотрудника. Всё, что может сотрудник, может любой посетитель: аудит, замечание R-2.3-1.
- Студенты других вузов жалуются на слетающий вход; короткая сессия безопаснее: [сводка](../research/SUMMARY.md), ЯД-1.
- Next.js не даёт ни хеша, ни защиты от перебора, ни флагов куки. Пример входа из его документации слабее требований и не гасит сессию при выходе: R-1.5, раздел 3 и раздел 5.
- Числа OWASP и NIST в R-1.5 прочитаны в пересказе и человеком не сверены: R-1.5, раздел 6.

## Варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Готовая библиотека входа | Хеш, куки и лимиты часто уже есть | Умолчания у каждой свои; у Better Auth параметры хеша не названы, остальные не проверялись: R-1.5, раздел 6. Растущую задержку по паре «адрес и аккаунт» и запреты для тестовых аккаунтов всё равно писать самим |
| Б. Свой вход: таблица сессий в PostgreSQL | Полный контроль; каждое правило — свой тест; выход гасит сессию | Всё пишется руками; ошибку поймают только тесты и аудит |

## Решение
Вариант Б — решение проекта. Довод: правила для публичных тестовых аккаунтов нестандартны, и их всё равно пришлось бы писать поверх библиотеки, умолчания которой не проверены.

**Аккаунты.**
- Регистрации, смены пароля, смены контактов и сброса пароля в прототипе нет. Аккаунты создаёт скрипт вымышленных данных. Запросов на эти действия у сервера просто нет: проверка Т-01.
- Роли две: студент и сотрудник. Администратора нет.
- Все аккаунты прототипа — тестовые. У каждого два признака:
  - **набор** — к какому набору тестовых аккаунтов он относится: основной или один из резервных. Набор — граница области сотрудника: [ADR-0002](ADR-0002-data-access.md);
  - **пароль опубликован** — да у основного набора, нет у резервного, пока его не выдали жюри.

**Пароль.**
- Хранится только хеш. Алгоритм — scrypt из стандартной библиотеки Node.js, параметры N = 2^16, r = 8, p = 2. Это один из допустимых наборов таблицы OWASP по R-1.5, находка F13, проверка В-01.
- Умолчания `crypto.scrypt` ниже порога: параметры задаются явно. Предел памяти `maxmem` тоже задаётся явно — 128 МиБ: по умолчанию он 32 МиБ, и вызов с N = 2^16 упал бы — R-1.5, находка F16. Снижать N, чтобы вызов прошёл, нельзя.
- Вызов только асинхронный: `scryptSync` на время счёта останавливает весь сервер. Хеши сравниваются функцией постоянного времени `timingSafeEqual`. Поле пароля на входе — не длиннее 256 символов: длиннее — отказ до счёта хеша.
- Соль случайная, своя у каждого пароля. В строке хеша записаны алгоритм и параметры — их можно усилить без смены схемы.
- Почему не Argon2id, первый в списке OWASP: стабильность `crypto.argon2` в Node.js в ресерче не найдена, а отдельный пакет — новая зависимость с непроверенной лицензией. Это решение проекта; при замене меняется одна функция.
- Проверка В-02 «политика пароля» не применяется: пользователь пароль не задаёт. Пароли основных тестовых аккаунтов публичны по заданию. Пароли резервных задаёт команда — правило ниже.

**Сессия.**
- После верного пароля сервер создаёт случайный токен — 32 байта от криптографического генератора. Токен уходит в куку; в базе лежит только его хеш SHA-256, номер пользователя, время создания, срок и адрес, с которого сессия создана.
- Кука: имя с префиксом `__Host-`, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, без `Domain`, срок задан. Префикс советует OWASP: R-1.5, находка F19.
- Флаг `Secure` ставится всегда, и на ноутбуке тоже. Локальный запуск идёт по `http://localhost`; что браузер принимает там такую куку с префиксом — знание оркестратора, по документации не сверено. Проверка — сквозной тест пакета 2.4. Тест не прошёл — префикс снимается, флаг остаётся; это записывается сюда.
- Срок сессии — 7 суток от входа, без продления. Это выбор проекта: длиннее, чем OWASP советует для простоя, короче верхней границы NIST в 30 суток — R-1.5, находка F20. Довод: вход не должен слетать, а действий с высокой ценой ошибки в прототипе нет.
- Выход удаляет строку сессии. Каждый вход создаёт новый токен. Просроченная сессия не принимается.
- С одного аккаунта можно войти с нескольких устройств: один тестовый аккаунт откроют несколько членов жюри.
- Предел живых сессий: не больше 10 на пару «аккаунт и адрес» и не больше 300 на аккаунт. При превышении удаляется самая старая сессия той же пары, затем — самая старая сессия аккаунта. Числа — выбор проекта.
- Секретного ключа для подписи у сессий нет: токен случайный и проверяется по базе.

**Ответ на неверный вход.**
- Текст и код ответа одинаковы для «нет такого логина» и «неверный пароль». Для несуществующего логина хеш всё равно считается, чтобы время ответа не выдавало разницу: проверка В-05.
- Счётчики ведутся по введённой строке логина, а не по номеру пользователя. Несуществующий логин получает те же задержки и тот же ответ 429, что и настоящий: иначе по коду ответа можно узнать логины резервного набора. В проверку В-05 добавляется шаг: по семь неверных попыток на настоящий и на выдуманный логин — коды ответов совпадают.
- Адрес возврата после входа — только внутренний путь: проверка В-12.

**Защита от перебора.** Числа — выбор проекта; источники дают границы.
| Счётчик | Правило | Зачем |
|---|---|---|
| Пара «адрес и логин» | Пять неверных попыток — без задержки. Дальше ожидание удваивается: 1, 2, 4 секунды и так до 5 минут. Сбрасывается верным входом или через 15 минут тишины | Решение пользователя: задержка вместо блокировки. Посторонний замедляет только себя |
| Адрес | Не больше 30 попыток входа за 10 минут, верных и неверных вместе; дальше — ответ 429 до конца окна | Перебор по многим аккаунтам с одного адреса; поток верных входов по публичному паролю, каждый из которых — дорогой хеш и новая сессия |
| Логин, пароль которого не опубликован | 100 неверных попыток подряд — вход по этому логину закрывается, пока команда не откроет его скриптом. Счётчик сбрасывается только верным входом | Верхняя граница NIST: R-1.5, находка F14. Это резервные аккаунты до выдачи жюри |

- **Попытка записывается до проверки пароля.** Запись и чтение счётчика — одна атомарная операция в базе: вставка строки попытки или `UPDATE … RETURNING`. Отказ даётся по её результату. Схема «прочитать счётчик, посчитать хеш, потом увеличить» запрещена: залп одновременных запросов прошёл бы проверку целиком — аудит, замечание R-2.3-2. В проверку В-04 добавляется параллельный шаг: 50 одновременных неверных попыток, из них хеш считается не больше чем для разрешённого числа.
- **Исключение из границы NIST.** У логинов с опубликованным паролем счётчика «100 попыток» нет: подбирать публичный пароль незачем, а закрытие входа дало бы любому посетителю способ не пустить жюри. Это решение проекта.
- Ожидание — это ответ 429 с временем до следующей попытки, а не удержание соединения.
- Счётчики лежат в базе, не в памяти приложения.
- **Адрес посетителя** берётся из одного заголовка, который ставит свой обратный прокси. Значение, присланное посетителем, прокси затирает. Мимо прокси до приложения не дойти: порт приложения наружу не публикуется — [ADR-0001](ADR-0001-stack.md). Иначе счётчик сбрасывается подменой заголовка: проверка В-04, с попыткой мимо прокси.
- Адрес IPv6 считается по сети /64: у одной машины их целая сеть.
- Лимит по адресу считается до вычисления хеша: хеш дорогой, и поток запросов иначе занял бы память сервера.

**Тестовые аккаунты.**
- Основной набор — два студента с разными данными и сотрудник: ТР-11. Их логины и пароли идут в комментарий к работе. Класть ли их ещё и в README — не решено: [ADR-0004](ADR-0004-secrets-config.md).
- Резервный набор — решение пользователя от 11.11.2026: такой же набор с другими логинами. Сколько резервных наборов — решает пакет 3.8; не меньше одного.
- **Наборы не видят друг друга.** Сотрудник набора видит и меняет только заявки студентов своего набора: [ADR-0002](ADR-0002-data-access.md). Тот, кто портит заявки под основным сотрудником, до резервного набора не дотянется. Без этого резервные аккаунты цели не достигали: аудит, замечание R-2.3-1.
- **Пароли резервных аккаунтов** не публикуются и в git не лежат. Каждый — случайная строка не короче 20 символов от генератора: граница NIST для пароля как единственного фактора — 15, R-1.5, находка F14. Задаются переменными окружения при создании данных.
- **Выдача резерва.** Основной аккаунт испорчен — капитан заменяет комментарий к работе и запускает скрипт «набор опубликован»: признак «пароль опубликован» ставится, счётчик «100 попыток» с набора снимается.
- Проверка, что резервный набор входит: тест создаёт набор с паролями-метками и входит под каждым аккаунтом.
- **Лимит записи.** Не больше 10 заявок в сутки на пару «аккаунт и адрес» и не больше 200 в сутки на аккаунт; длина полей ограничена. Числа — выбор проекта. Общий лимит на аккаунт без пары позволил бы любому посетителю двадцатью заявками закрыть подачу для жюри: аудит, замечание R-2.3-4.
- **Лимит смены статуса** сотрудником — не больше 30 в минуту на аккаунт: [ADR-0002](ADR-0002-data-access.md).
- Автоматического ночного сброса данных нет: критерий жюри — «данные сохраняются», а сброс стёр бы заявку, поданную членом жюри накануне. Это решение проекта.
- **Чистка спама — не сброс.** У сессии записан адрес, у заявки — сессия, которая её создала. Скрипт чистки удаляет заявки, созданные с названных адресов или за названный промежуток, и показывает число строк до удаления. Заявки с других адресов он не трогает. Полный сброс набора — крайняя мера; запускает команда вручную.

**Подделка запросов.** Данные меняют только действия на сервере: Next.js сверяет для них Origin и Host. Поведение при отсутствии заголовка Origin в документации не описано — проверяется тестом В-10. Выход — тоже действие, а не ссылка. Если за прокси понадобится настройка `serverActions.allowedOrigins`, в ней стоит только свой домен, без шаблона `*`: R-1.5, находка F22.

## Последствия
- Что становится проще: каждое правило проверяется своим тестом; нет зависимости с непроверенными умолчаниями; нет секрета подписи.
- Что становится сложнее: код входа пишут ассистенты с нуля; ошибку в нём поймают только тесты В-01…В-12 и два аудита.
- Что нужно сделать: в пакете 2.4 — хеш, сессия, кука, выход, признаки «набор» и «пароль опубликован»; в пакете 3.1 — счётчики, одинаковые ответы, лимиты, пределы сессий; в пакете 3.8 — резервные наборы, скрипты «набор опубликован» и чистки.
- Слабые места:
  - **Публичный аккаунт можно портить.** Посетитель под основным сотрудником может отклонять заявки основного набора, пока хватает лимита. Спасает замена набора на резервный, а не запрет.
  - Члены жюри за одним адресом сети делят лимит по адресу: 30 входов за 10 минут и 10 заявок в сутки на аккаунт. Чужой перебор с того же адреса задержит и их — до 10 минут.
  - Пределы «на аккаунт» — 300 сессий, 200 заявок в сутки — можно исчерпать с многих адресов. Тогда старые сессии жюри гасятся, а подача закрывается до конца суток. Цена атаки — сотни адресов; ответ — резервный набор.
  - Резервный логин можно закрыть сотней неверных попыток. Для этого надо знать логин: ответы входа его не выдают.
  - Хеш scrypt с N = 2^16 занимает около 64 МиБ памяти на одно вычисление — расчёт оркестратора по формуле 128 · N · r байт; аудит расчёт подтвердил. На сервере не измерено. По знанию аудитора, не сверенному с документацией: асинхронный scrypt идёт в пуле из четырёх потоков, так что памяти уходит не больше примерно 256 МиБ, а входы встают в очередь. Лимит по адресу стоит до хеша именно поэтому.
  - Семь суток жизни сессии на общем телефоне — риск; кнопка «Выйти» есть в профиле.

## Простыми словами
Пароль в базе не хранится: хранится его отпечаток, из которого пароль не вычислить обратно. После входа сайт выдаёт телефону случайный пропуск на семь дней, а у себя записывает только отпечаток пропуска. Кнопка «Выйти» уничтожает пропуск на сервере.

Если кто-то подбирает пароль, сайт заставляет его ждать всё дольше. Навсегда аккаунт не закрывается: пароли тестовых аккаунтов известны всем, и такая блокировка закрыла бы вход жюри. Но если с одного адреса идёт слишком много попыток, сайт на несколько минут перестаёт принимать вход с этого адреса.

Тестовые аккаунты открыты всем, поэтому их могут испортить. На этот случай есть запасные наборы аккаунтов. Наборы отделены друг от друга: испортив один, до другого не добраться.

## Как проверяем
- Тест или проверка: В-01, В-06, В-07 — с М0 (пакеты 2.4 и 2.6); В-03…В-05, В-08…В-10, В-12, Т-01, Т-04, Т-07 — после пакета 3.1: [ADR-0005](ADR-0005-security-checks.md).
- Результат: ожидается.
