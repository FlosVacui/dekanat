# ADR-0002: данные и слой доступа — владелец записи берётся из сессии

| | |
|---|---|
| Статус | принято 11.11.2026 после двух раундов аудита |
| Дата | 11.11.2026; доработан 11.11.2026 по аудиту: [RV-2.3-1](../reviews/RV-2.3-1.md), [RV-2.3-2](../reviews/RV-2.3-2.md) |
| Кто решил | Оркестратор; правило «владелец из сессии» — из `CLAUDE.md` |
| Связано | ЗД-5, ТР-9.1, ТР-5, ТР-11, ЯД-4; [ADR-0001](ADR-0001-stack.md), [ADR-0003](ADR-0003-auth-sessions.md); проверки П-01…П-12 из [R-1.5](../research/R-1.5.md), раздел 4.1 |

## Контекст
- Задание: «чужой профиль или заявку не открыть, даже подставив другой адрес» — ТР-9.1; студент видит только свои данные — ЗД-5.
- Next.js не проверяет владельца записи сам. Проверка только на входе в раздел или в общей обёртке страниц не защищает: R-1.5, раздел 3, строка «Чужие данные».
- В прототипе две роли: студент и сотрудник. Сотрудник меняет статус заявки: ЯД-4.
- Пароль сотрудника публичен, как и пароли студентов: всё, что может сотрудник, может любой посетитель. Аудит, замечание R-2.3-1.
- В адресах есть номера записей: `/requests/<id>` — номер заявки, `/grades/<id>` — номер дисциплины: [карта экранов](../design/S-2.1-scenarios.md).

## Варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Проверка владельца в каждой странице и в каждом действии по отдельности | Не нужен общий слой | Одна забытая проверка — утечка; аудитору нужно читать весь код |
| Б. Один слой доступа к данным: запрос к базе возможен только через него, и каждая функция слоя получает того, кто спрашивает | Проверка в одном месте; аудитор читает один каталог; так советует документация Next.js: R-1.5, раздел 5 | Дисциплина: мимо слоя ходить нельзя — нужна проверка поиском по коду |
| В. Вариант Б и политики строк в PostgreSQL (RLS) | Вторая линия защиты | Отдельная роль базы, политики и тесты: R-1.5, раздел 5 — «по желанию» |

## Решение
Вариант Б. RLS в М0 не включается; к нему можно вернуться на этапе 4 — это решение проекта из-за срока.

Правила слоя:
1. **Запросы к базе — только в `app/src/server/dal/`.** Модуль помечен `server-only`. Страницы и действия клиент базы не импортируют.
   - Запросы сессий и счётчиков входа тоже лежат в слое. В `app/src/server/auth/` — логика входа без клиента базы.
   - Исключение одно, поимённо: скрипты в `app/db/` — миграции, вымышленные данные, чистка. Они не часть работающего приложения и запускаются командой. Поиск по коду их пропускает.
2. **Первый аргумент каждой функции — действующее лицо:** номер пользователя, роль, набор и группа, прочитанные из сессии на сервере. Номер студента из адреса, формы или тела запроса в слой не передаётся.
   - У действующего лица свой тип, и создаёт его только модуль сессий — это решение проекта. Тип — с меткой: класс с закрытым полем или поле `unique symbol`. Обычный тип TypeScript сверяется по форме, и самодельный объект с теми же полями проверку типов прошёл бы: аудит, замечание R-2.3-28, знание аудитора. Приведение `as` к этому типу и создание метки вне модуля сессий запрещены; поиск по коду считает их находкой.
   - Сам принцип — проверка прав в слое, владелец из сессии — из документации Next.js: R-1.5, находка F7. Про тип действующего лица в ней ничего нет.
3. **Запись по номеру ищется вместе с владельцем:** условие «номер записи и владелец» в одном запросе. Не найдено — ответ «нет такой записи», одинаковый для чужой и для несуществующей.
   - У записей группы — дисциплина, работа, пара, объявление — условие «номер записи и группа из профиля». Чужая дисциплина по адресу `/grades/<id>` — тот же ответ «нет такой записи».
   - Функции студента первым делом проверяют роль. Сотрудник на адресе студента получает отказ, а не пустую страницу с кодом 200.
4. **Списки** всегда ограничены владельцем. Параметра «чей список» у студента нет.
5. **Наружу — только нужные поля.** Функции слоя возвращают объекты с перечисленными полями. Хеш пароля и внутренние поля из слоя не выходят.
6. **Изменение — по списку разрешённых полей.** Владелец и роль из тела запроса не принимаются никогда. Студент статус не передаёт. Сотрудник передаёт только целевой статус, и он проверяется по списку допустимых переходов. Ввод проверяется на сервере: тип, длина, допустимые значения.
7. **Номера записей в адресах — случайные (UUID).** Это не защита, а помеха перебору; защита — правило 3.
8. **Запросы только с параметрами.** Сортировка — по списку разрешённых столбцов.
9. **Личное не кэшируется.** `use cache` и `unstable_cache` к личным данным не применяются; личные ответы уходят с `Cache-Control: private, no-store`. Это рекомендация автора R-1.5, а не требование Next.js.

Область сотрудника — решение проекта:
- **Граница — набор.** Сотрудник привязан к своему набору тестовых аккаунтов: [ADR-0003](ADR-0003-auth-sessions.md). Он видит и меняет только заявки студентов своего набора. Заявка чужого набора для него — «нет такой записи». В настоящем вузе на этом месте стоял бы деканат своего факультета.
- **Почему так.** Пароль сотрудника публичен. Без границы посетитель под основным сотрудником отклонял бы заявки и резервных студентов, и замена аккаунтов на резервные ничего бы не дала: аудит, замечание R-2.3-1.
- **Видит:** список заявок своего набора; в заявке — ФИО и группу студента, вид, даты, текущий статус и историю статусов.
- **Не видит:** оценки, расписание, остальной профиль, уведомления студента.
- **Меняет:** статус — только по допустимым переходам из [S-2.1, раздел 5](../design/S-2.1-scenarios.md); при отклонении — причину, одну из списка. Сроки и кабинет в текстах статусов сервер подставляет сам по виду заявки. Любое другое поле в запросе отбрасывается, недопустимый переход отклоняется.
- **Смена статуса — один запрос с условием на текущий статус:** `UPDATE … WHERE` номер, набор и статус «из какого». Строк изменено ноль — отказ. Иначе два сотрудника, нажавшие разное одновременно, увели бы заявку по запрещённому пути: аккаунт сотрудника у жюри общий.
- **Лимит:** не больше 30 смен статуса в минуту на пару «аккаунт сотрудника и адрес». Число — выбор проекта. Лимит на аккаунт без пары посетитель тратил бы за члена жюри. Он не останавливает порчу заявок, а замедляет её.
- Каждая смена статуса пишет строку в историю заявки и создаёт уведомление владельцу — и только ему.
- Функции сотрудника лежат отдельно и первым делом проверяют роль. Публичного аккаунта администратора нет.

Таблицы — намерение, имена уточнит пакет 2.4:

| Таблица | Что хранит | Владелец |
|---|---|---|
| `users` | Логин, хеш пароля, роль, набор, признак «пароль опубликован» | — |
| `students` | ФИО, факультет, направление, курс, группа | Пользователь |
| `sessions`, `login_attempts` | Сессии и счётчики попыток: [ADR-0003](ADR-0003-auth-sessions.md) | Пользователь |
| `lessons`, `lesson_changes` | Расписание группы и изменения | Группа |
| `disciplines`, `assignments` | Дисциплины и работы со сроками | Группа |
| `grades` | Баллы и итоги по дисциплинам | Студент |
| `requests`, `request_events` | Заявки и история статусов; у заявки записан адрес, с которого она подана | Студент |
| `announcements`, `notifications` | Объявления деканата; личные уведомления с отметкой о прочтении | Группа или факультет; студент |
| `announcement_reads` | Отметка «студент прочитал объявление» | Студент |

Расписание, дисциплины, работы и объявления принадлежат группе: студент видит их по своей группе из профиля, а не по группе из адреса.

Библиотека запросов выбирается первым шагом пакета 2.4. Условия: лицензия подтверждена на странице проекта; стабильная версия; запросы с параметрами; миграции файлами в git. Не выполняются — берётся драйвер PostgreSQL и запросы с параметрами руками.

Роль базы у приложения — без прав суперпользователя и без обхода политик строк. Порт базы наружу не публикуется.

## Последствия
- Что становится проще: аудит — один каталог; тесты — одна матрица «роль — адрес — действие».
- Что становится сложнее: каждая новая страница обязана идти через слой; нужна проверка поиском по коду, что клиент базы не импортируется вне слоя и вне `app/db/`.
- Что нужно сделать: в вымышленных данных у каждого студента — своя метка во всех пяти разделах ядра, чтобы тест искал чужую метку в ответе: R-1.5, раздел 4, «Общая подготовка».
- Чего это решение не даёт: второй линии защиты в базе. Ошибка внутри слоя ничем не подстрахована, кроме тестов.
- Слабое место: внутри своего набора посетитель под сотрудником по-прежнему может отклонять заявки. Отклонённую заявку студент подаёт снова кнопкой «Подать снова»; если порча не прекращается, набор меняют на резервный.

## Простыми словами
Сайт никогда не спрашивает у телефона «чьи данные показать». Он сам знает, кто вошёл, и достаёт из базы только записи этого человека. Если подставить в адрес номер чужой заявки, сайт ответит «такой заявки нет» — так же, как на выдуманный номер. Все обращения к базе собраны в одном месте, чтобы проверяющий мог просмотреть их целиком. Сотрудник деканата видит заявки только своих студентов и меняет только их статус; оценок и расписания он не видит. Запасной набор тестовых аккаунтов отделён от основного: сотрудник одного набора не видит заявок другого.

## Как проверяем
- Тест или проверка: П-01, П-02, П-04, П-05, П-06, П-10, П-12 — с М0 (пакеты 2.4 и 2.6); П-03, П-07, П-08, П-09 — по мере появления экранов: [ADR-0005](ADR-0005-security-checks.md). В П-12 добавлен шаг «сотрудник одного набора не видит заявок другого»; в П-05 — «сотрудник на адресах студента получает отказ». Порядок переходов статуса — своя проверка проекта ПР-1. Поиск по коду: импорт клиента базы вне `server/dal/` и `app/db/`.
- Результат: ожидается.
