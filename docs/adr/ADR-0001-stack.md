## Контекст
- Задание требует работающий прототип по ссылке и стек, «гибкий к росту числа пользователей»: ТР-1, ТР-2.
- Код пишут ИИ-ассистенты, человек ставит задачу и проверяет поведение: ТР-3. Участник А читает код, но не пишет его: [DECISIONS](../DECISIONS.md#решения-при-утверждении-плана-10112026).
- Ресерч: варианты 1 и 2 оба подходят; сильного довода против варианта 2 нет; отчёт R-1.4 ревью не проходил — [сводка](../research/SUMMARY.md), раздел 5, Р-3.
- Сервер — один VPS у российского провайдера, 2 ядра и 2 ГБ памяти: сводка, раздел 6.

## Варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Next.js и TypeScript, PostgreSQL, Docker Compose | Интерфейс и сервер в одном проекте; вход, база и тесты на 360 пикселях возможны: R-1.4, раздел 3.3 | Проверку владельца записи, хеш пароля, защиту от перебора и флаги куки стек сам не даёт: R-1.5, раздел 3 |
| 2. FastAPI с шаблонами | Тоже подходит: R-1.4, раздел 3.3 | Мобильный интерфейс потребует больше ручной работы — предположение исследователя |
| 3. Готовый сервис данных | Быстрый старт | Доступ из России не подтверждён; на своём сервере сводится к варианту 1 |

## Решение
Вариант 1 — решение пользователя от 11.11.2026.

Устройство — решение проекта:
1. **Одно приложение Next.js**, маршруты App Router. Страницы собираются на сервере.
2. **Данные меняются только действиями на сервере** (Server Actions). Отдельного открытого API в М0 нет. Появится обработчик маршрута, который меняет данные, — он сам сверяет заголовок Origin: R-1.5, раздел 3, строка «Подделка запросов».
3. **Версия Next.js — не ниже 16.4.5:** выпуск безопасности от 03.11.2026 — R-1.5, проверка Д-03. Версии закрепляются файлом блокировки; установка — `npm ci`.
4. **База — PostgreSQL в соседнем контейнере.** Порт наружу не публикуется.
   - **Порт приложения наружу тоже не публикуется.** Снаружи открыт только обратный прокси; до приложения он доходит по внутренней сети Docker. Запрос прямо в порт приложения обошёл бы HTTPS и позволил бы посетителю самому задать свой адрес для счётчиков входа: аудит, замечание R-2.3-3.
   - **Данные переживают перезапуск.** Файлы базы лежат в именованном томе Docker: перезапуск и пересборка контейнеров их не стирают. Копия базы — `pg_dump` раз в сутки на том же сервере; настраивает пакет 2.5. Копии вне сервера в прототипе нет.
5. **Интерфейс — Tailwind и shadcn/ui**, как в [ROADMAP, раздел 4](../ROADMAP.md). Размеры кнопок задаются самим: из коробки они ниже 44 пикселей — сводка, раздел 5, Р-3.
6. **Тесты — Vitest и Playwright.** Сценарии — на 360×800.
7. **Приложение не хранит состояние в памяти.** Сессии и счётчики попыток входа лежат в базе: [ADR-0003](ADR-0003-auth-sessions.md).
8. **На ноутбуке разработки Docker нет** — решение пользователя от 11.11.2026: «Дальше мы же будем БД делать на сервере». Локально PostgreSQL той же основной версии запускается без контейнера, приложение — командой npm. Приложению всё равно, где база: оно получает строку подключения. Файлы Compose пишет пакет 2.4, первый раз запускает пакет 2.5 на сервере.

## Схема роста
Прототип рассчитан на жюри и пробу: десятки посетителей. Ниже — что меняется при росте. Ничего из этого не измерено: нагрузочных замеров нет.

| Ступень | Что упирается | Что делаем | Что уже заложено |
|---|---|---|---|
| Один сервер, один контейнер приложения | — | Как сейчас | — |
| Больше посетителей, чем тянет один контейнер | Процессор приложения | Несколько копий приложения за балансировщиком | Состояния в памяти нет: сессии и счётчики в базе — любая копия обслужит любой запрос. Условия: у всех копий один образ; балансировщик передаёт адрес посетителя тем же заголовком, что и прокси; число копий, умноженное на размер пула соединений, не больше предела соединений PostgreSQL |
| База становится узким местом | Диск и память PostgreSQL | База выносится на отдельный сервер или в управляемый сервис; для чтения — реплика | Все запросы идут через один слой доступа: адрес базы меняется в одном месте. Условие: сессии и счётчики входа читаются только с основной базы — иначе сессия после выхода живёт, пока реплика отстаёт |
| Много одинаковых файлов | Сеть | Файлы интерфейса раздаёт сеть доставки | Next.js даёт файлам имена с хешем и долгий срок кэша: R-1.5, раздел 3, строка «Заголовки» |
| Много уведомлений и рассылок | Время ответа | Очередь фоновых задач | Уведомление — строка в таблице; создание отделено от показа |
| Несколько вузов или факультетов | Модель данных | Поле организации в таблицах и в проверке доступа | Проверка доступа — в одном слое: [ADR-0002](ADR-0002-data-access.md) |

Личные данные не кэшируются общим кэшем ни на одной ступени: [ADR-0002](ADR-0002-data-access.md).

## Последствия
- Что становится проще: один язык и один проект для интерфейса и сервера; один образ для сервера и запасного провайдера.
- Что становится сложнее: защита делается руками — владелец записи, хеш, перебор, куки, заголовки. Пример входа из документации Next.js копировать нельзя: сводка, ЯД-1.
- Что нужно сделать: пакет 2.4 создаёт проект в `app/`; первым шагом сверяет лицензии и версии зависимостей на страницах проектов и пишет их в `THIRD_PARTY.md`.
- Что не проверено: файлы Compose до сервера никто не запускал — на ноутбуке разработки Docker нет. По знанию аудитора, не сверенному с документацией: у нескольких копий приложения должен совпадать ключ шифрования действий на сервере, его задаёт сборка — отсюда условие «один образ». Доступ к npm и Docker Hub с российского сервера — R-1.4, находки Z1–Z4. Не заработает — образ собирается на ноутбуке и переносится на сервер; это предположение исследователя.

## Простыми словами
Кабинет — один сайт. Страницы собирает сервер, а в телефон приходит уже готовая страница. Данные лежат в базе рядом с сайтом, и снаружи к базе не подойти. База хранит данные на диске сервера отдельно от самого сайта: сайт можно перезапустить или обновить, и заявки с оценками останутся на месте. Сайт ничего не помнит «в голове»: кто вошёл, записано в базе. Поэтому при росте числа студентов можно запустить несколько копий сайта, и любая из них обслужит любого студента.
