## Контекст
- Задание: ключи и пароли сервисов не лежат в коде и в браузере пользователя — ТР-9.3.
- Репозиторий может стать публичным: развилка Р-8 не решена, срок — 20.11. Всё, что попало в историю git, тогда увидят все.
- С кодом работают ИИ-ассистенты. Чтение `.env` им запрещено настройками, но не проверено, закрывает ли запрет чтение через командную строку и файлы в подпапках: IMP-008. Запрет записан только для файлов в корне репозитория. Продукт лежит в `app/`, и `app/.env*` под запрет не попадает.
- В Next.js переменная с приставкой `NEXT_PUBLIC_` попадает в браузер; остальные остаются на сервере: R-1.5, раздел 3, строка «Секреты».

## Варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Секреты в `.env` на сервере, в образ не входят, передаются при запуске | Просто; подходит одному серверу | Файл на сервере хранит человек; копию надо беречь |
| Б. Хранилище секретов провайдера | Удобнее при росте | Лишняя настройка для одного сервера; привязка к провайдеру |

## Решение
Вариант А — решение проекта.

**Какие секреты есть.**
- Пароли базы — два: у владельца базы, под которым идут миграции, и у роли приложения без прав суперпользователя. Строка подключения приложения.
- Пароли резервных тестовых аккаунтов.
- Закрытый ключ сертификата и данные его выпуска у обратного прокси. Папка данных прокси лежит вне репозитория.
- После решения по Р-5 — ключ модели.
- Ключа подписи сессий нет: [ADR-0003](ADR-0003-auth-sessions.md).
- По знанию аудитора, не сверенному с документацией: при нескольких копиях приложения появится ещё ключ шифрования действий на сервере. В прототипе копия одна.

**Где лежат.**
- Настоящие значения — только в `.env` на сервере. Файл создаёт и хранит участник А.
- На ноутбуках — `.env` с локальными значениями, которые ничего не открывают: пароль локальной базы. Настоящих значений сервера на машинах, где работают ассистенты, нет. Так запрет чтения `.env` перестаёт быть единственной защитой.
- В git — только `.env.example`: имена переменных без значений.
- Файл окружения один — в корне репозитория. В `app/` файлов `.env*` нет: туда запрет чтения для ассистентов не дотягивается. Запрет на `app/.env*` добавляется в настройки ассистентов после согласия пользователя: это общий файл.
- `.env*` стоит в `.gitignore` и в `.dockerignore`. Пакет 2.4 проверяет это сам: шаблон `create-next-app` добавляет строку в `.gitignore`, собранный руками проект — нет.

**В коде.**
- `process.env` читается в одном файле — `app/src/server/config.ts`, помеченном `server-only`. Остальной код берёт значения из него. Исключение одно, поимённо: скрипты в `app/db/` — миграции, вымышленные данные, чистка. Они запускаются командой и читают свои переменные сами.
- Секрет никогда не получает имя с `NEXT_PUBLIC_`. Ключа `env` в конфигурации Next.js нет.
- Карты кода для браузера в рабочей сборке выключены.

**В образе Docker.** Секреты передаются контейнеру при запуске. В Dockerfile нет `ARG` и `ENV` с секретами.

**Каждому — только своё.** Контейнер приложения получает переменные поимённо: строку подключения своей роли и больше ничего. Пароль владельца базы получают только база и миграции. Пароли резервных аккаунтов — только скрипт данных при запуске. Весь `.env` целиком контейнеру приложения не передаётся.

**На сервере секреты видит человек.** Команды, которые печатают значения окружения, на сервере запускает участник А, а не ассистент: `docker compose config`, `docker inspect`, `docker history --no-trunc`, `env` и `printenv` в контейнере, чтение `.env`. Ассистент на сервере в пакете 2.5 готовит команды и читает вывод, в котором значений нет. Вывод с настоящими значениями в чат и в отчёты не копируется.

**Заголовки.**
- В приложении: `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, запрет встраивания в чужие страницы, политика содержимого без `unsafe-eval`; заголовок `X-Powered-By` убран.
- На обратном прокси: перенаправление на HTTPS и `Strict-Transport-Security`.
- Личные ответы — `Cache-Control: private, no-store`: [ADR-0002](ADR-0002-data-access.md).
- Полный текст политики содержимого пишется в пакете 2.6 на работающем приложении.

**Ошибки и журналы.**
- Посетитель видит общий текст ошибки. Текст внутренней ошибки, путь и запрос к базе наружу не уходят.
- В журнал не пишутся пароли, токены и куки сессий, ФИО и тела запросов целиком.
- В журнал пишутся события защиты: неверный вход, отказ в доступе, срабатывание лимита — с временем и номером пользователя.

**Проверки без чтения секретов.** Тесты подставляют вместо секретов метки и ищут метки в файлах для браузера и в журналах: R-1.5, проверки С-03 и Ж-02. Настоящие значения ассистент не читает и не печатает. `gitleaks` запускается только с `--redact`.

**Поправка к проверке С-05 по IMP-012.** Команда `docker history --no-trunc` печатает значения `ENV` и `ARG`. Она запускается только на тестовом образе, собранном с метками вместо секретов; её вывод с настоящего образа в отчёты не копируется. В папку сборки тестового образа кладётся `.env` с метками, и метка ищется в файлах образа по именам файлов: так ловится и `COPY` файла окружения, а не только `ARG` и `ENV`.

## Последствия
- Что становится проще: одно место чтения окружения — одна строка поиска для аудитора; утечка локального `.env` ничего не открывает.
- Что становится сложнее: сервер настраивает человек; при потере `.env` сервера пароли задаются заново.
- Что нужно сделать: `.env.example` и `config.ts` — пакет 2.4; `.env` сервера — пакет 2.5, участник А; исключения `gitleaks` для публичных паролей основных тестовых аккаунтов — пакет 2.6, возможность не проверена: R-1.5, проверка Т-06.
- Слабое место: пароли основных тестовых аккаунтов публичны. Задание требует их только в комментарии к работе. Класть ли их ещё и в README — решение проекта, и оно не принято: README для жюри — пакет 5.3, а в открытом репозитории пароль сотрудника прочтёт любой, не только жюри. До ответа пользователя паролей в README нет; вопрос решается вместе с Р-8. Это не секрет сервиса, но сканер может принять такие пароли за находку.

## Простыми словами
Пароль от базы и другие ключи записаны в одном файле на сервере. В коде, в истории git и в том, что получает телефон, их нет. На ноутбуках, где с кодом работают ИИ-ассистенты, лежат только учебные значения, которые ничего не открывают. Проверки ищут в файлах сайта не настоящие ключи, а специальные метки: так проверяющему не нужно видеть сами ключи.
